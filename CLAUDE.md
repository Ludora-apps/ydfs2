# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

LinuxConsole (ydfs2): a source-based Linux distribution build system (fetches and compiles packages from source, LFS/Arch-style — not `.deb`/`.rpm`). The active branch is `2.12`; almost everything distro-related lives under `2.12/`. `webui/` is a separate Go + React application that drives the same build scripts through a browser instead of the command line. `wubi/` is an unrelated Windows-based installer subproject.

Two ways to build the distro, both driving the same `2.12/scripts/*` inside the same Docker image:
1. Command line at the repo root (`make ...`), which shells into `2.12/Makefile-docker` → `2.12/Makefile` inside a container.
2. The web UI (`webui/`), which snapshots the working tree and runs the identical `make` targets in Docker, streaming logs to a browser.

## Common commands

### Distro build (root `Makefile`)

```sh
make            # fast ISO: downloads prebuilt core/kernel, builds updates + ISO (needs a release tag)
make full        # full ISO: compiles everything from source, hours/days
make prepare      # create/chmod the host cache dirs under $HOME/2.12/* used by containers
make docker       # build the ydfs-2.12 Docker image
make iso          # build ISO only (assumes prepare/docker already done)
make verbose-iso    # same, with verbose compiler output
make busybox / linux / initramfs / updates / kde / mate / cinnamon   # build one component
make buildme       # retry a manual build after a failure (see TIPS.md)
make clean         # clean-docker
```

All of these ultimately run `cd 2.12 && DISTRONAME=linuxconsole make -f Makefile-docker <target>-docker`, which wraps `docker compose run`. `GIT_BRANCH` (used as the checkout subdir and cache path) is auto-detected from the current branch via `git rev-parse --abbrev-ref HEAD`, so these targets assume you're on `2.12` with a normal checkout layout (`~/2.12/...` caches next to the repo).

Skipping packages: edit `#SKIP` / `#STOP` markers in `2.12/packages/list-x86_64` (see `TIPS.md`). Kernel menuconfig / verbose / manual-build toggles go through `OPTION_BUILD=` in `2.12/Makefile-docker`.

### Web build manager (`webui/`)

```sh
cd webui
make build                              # tsc -b && vite build (UI) embedded, then go build -> ./ydfs-web
./ydfs-web --repo .. --dev --port 8080    # --dev disables auth; requires a loopback --host
make test                               # go test -race ./... (embeds UI first)
go vet ./...
YDFS_DOCKER_TEST=1 go test -race -run TestDockerLifecycle -v .   # real Docker lifecycle fixture (small Alpine image)
go test -race -run TestSettingsValidation -v .                  # run a single Go test
cd ui && npx playwright install chromium && npm test             # Playwright UI tests (builds.spec.ts)
```

For frontend-only iteration: `npm run dev` in `webui/ui` (Vite dev server) with the Go server started using `--origin http://localhost:5173`; Vite proxies `/api` to `:8080`. The compiled `ydfs-web` binary embeds the built UI (`internal/assets/dist`, generated by `make build`/`make ui`) via `internal/assets/assets.go` — Node is not needed at runtime, but **editing `webui/ui/src/*.tsx` requires rerunning `make build` (or `make ui`) to regenerate `internal/assets/dist` before a rebuilt `ydfs-web` binary reflects the change.**

Default data dir is `~/.local/share/ydfs-web` (override with `--data`); it holds the SQLite job DB, per-job source snapshots/output, all build logs in `logs-build/`, and the shared `build-home` cache — inspect it directly with `sqlite3 <data>/state.db "SELECT json_extract(data,'$.state') FROM jobs"` when debugging job state without a browser.

## Architecture: `webui/`

- `main.go` — HTTP server setup, auth/CSRF middleware, routing, `App` struct (holds the DB, mutex, wake channel, docker path). Auth model: in non-dev mode, requests must come from loopback, carry `X-Build-Proxy-Secret` matching `YDFS_PROXY_SECRET`, and `X-Forwarded-User` must be in the `YDFS_ALLOWED_USERS` allowlist — identity headers are meant to be stripped/set only by the reverse proxy (Caddy/Nginx + OAuth2 Proxy), never trusted from the browser directly. `presence()` uses that same identity as a heartbeat: every `GET /api/capabilities` (each open page polls it every 5s) stamps `App.seen[user]`, and the response's `others` lists everyone else stamped within `presenceWindow` (20s, three missed polls). The UI turns that into a standing amber banner, because one checkout, one profile table and one build queue are shared by everyone connected — it warns, it never blocks. An anonymous poll (dev mode behind no proxy) is never recorded.
- `model.go` — `Job`/`Settings`/`Profile` types, SQLite schema (`jobs`, `profiles` tables storing JSON blobs), `terminal(state)` (`succeeded`/`failed`/`cancelled`).
- `runner.go` — the actual build lifecycle:
  - `worker()` is a single-job polling loop (one build at a time by design): picks the next `running`/non-terminal job first (resume after restart), else the oldest `queued` job, checked against free disk space.
  - `run()` drives one job through `docker compose run --detach` (via `launch()`), polls container state with `docker inspect`, and transitions `queued → starting → running → succeeded|failed|cancelled` purely based on the container's actual exit code/status — never by parsing log content. `finish()` persists the terminal state.
  - `captureLogs()` tails `docker logs --follow` into a per-job `build.log` file, replaying/skipping already-persisted bytes after a server restart (so restarting the service does not lose or duplicate log history, and resumes monitoring already-running containers).
  - `collect()` validates that expected outputs exist and are nonempty (ISO file for `fast-iso`/`full-iso`, or the specific component binary/squashfs for component targets) before marking a job `succeeded` — exit code 0 alone is not sufficient.
  - `events()` is the SSE log endpoint: streams `build.log` from a byte offset (reconnect via `Last-Event-ID` or `?offset=`), and emits a terminal `done` event (closing the stream) only once the job state is terminal *and* no more log bytes are pending.
- `logs.go` — build logs. Every log lives in `<data>/logs-build/<job id>.log`, not under the per-job directory: they outlive the artifacts they describe and are listable, searchable and removable on their own. `logPath` is the single source of truth for that path and fails closed (returns `""`) on any id that is not plain filename characters; `migrateLogs` moves logs written by earlier versions out of `jobs/<id>/build.log` at startup, never overwriting a newer one. `GET /api/logs` lists them with their build's context, `DELETE /api/jobs/{id}/log` removes one (refused while the build is running, since `captureLogs` is still writing), and `deleteJob` removes the log explicitly — it no longer falls inside the directory it deletes, so a log must not be allowed to outlive its build.
- `vm.go` — the "Test in browser" console: boots a succeeded ISO in QEMU/KVM inside a container (`webui/vm/Dockerfile`, tag `ydfs-vm:1`, built by `make vm-image`) and proxies its screen to the browser. One VM at a time guarded by `App.vmMu` (never `App.mu`, so a console cannot block the build worker; lock order is `mu` → `vmMu`). `vmLaunch` runs an unprivileged container with only `/dev/kvm` passed in and the ISO bind-mounted read-only, resolving the ISO through the same `os.OpenRoot` guard as `downloadArtifact`. Two non-obvious constraints are load-bearing: QEMU's VNC primary must be a **UNIX socket** (`-vnc unix:/tmp/vnc.sock,websocket=5700`) or QEMU copies the primary's address onto the websocket listener and Docker's published port never connects — this also means no raw VNC port exists; and `vmConsole`'s `Rewrite` must restore the RFC spelling of `Sec-WebSocket-*` headers, because QEMU matches them case-sensitively while Go canonicalises them to `Sec-Websocket-*` (the handshake is otherwise reset with no reply). Readiness is `vmConsoleAnswers`, an HTTP probe rather than a TCP dial, because Docker's userland proxy accepts connections before QEMU is listening. `vmConsole` checks `Origin` itself: a WebSocket handshake is a GET and so escapes `handler()`'s CSRF rule. `vmWatch` stops a machine on idle/abandonment/age, `reapVMs` deletes anything labelled `ydfs-vm=1` at startup and after shutdown (sessions are ephemeral, never adopted), and `pruneLocked` skips the build a machine is booted from.
- `retention.go` — artifact retention and favourites. `pruneLocked` (caller must hold `App.mu`; called from `finish()` where the lock is already held, and once at startup) keeps the `keepBuilds` (3) most recent succeeded builds of each class — `iso` vs `component`, separate windows — plus every favourite, and deletes only the *artifacts* of the rest (an ISO is ~3.3 GB; the rest of a job dir is ~70 MB), setting `Job.PrunedAt` and leaving the row, log, `config.ini` and source snapshot intact. A favourite inside the window still consumes its slot, so an aged-out favourite cannot shrink the window. `setFavorite` pins/releases; `downloadConfig` serves the archived `config.ini`.
- `flathub.go` — the catalogue behind the UI's **Flatpak** screen: every application on Flathub (~3300), which the user can tick to have pre-installed in the ISO. Mirrors `repo.go`'s split — `GET /api/flathub` serves the cached catalogue with no network call (falling back to the built-in list in this file), `POST /api/flathub/refresh` pages through Flathub's popular collection (`flathubPageSize` at a time, most popular first) into `<data>/flathub.json`; a failure on the first page keeps the previous catalogue, a failure partway keeps the pages already read. It is deliberately **not** part of `GET /api/capabilities`, which every open browser polls every 5s — a few hundred kilobytes of catalogue is fetched once per page load instead. `allowedFlatpak` is the server-side allowlist (cached catalogue ∪ built-in), checked in `submit` so the browser's list is never authoritative.
- `repo.go` — the **Repository** screen: `GET /api/repository` reports the checkout (HEAD commit, branch, `detached` flag, nearest tag, dirty flag), the cached upstream commit with ahead/behind counts, and one `Source` per repository the checkout can be moved to — itself, the checkout's `origin` remote, and the fixed upstream — each carrying its branches and the `commitCount` (10) newest commits of the selected one. All of that is refs-only: rendering the screen never touches the network. `POST /api/repository/check` fetches every upstream branch by URL into `refs/remotes/upstream/*` (the fixed `https://github.com/linuxconsole-org/ydfs2`; only tests substitute `upstreamFrom`) and then the `origin` remote — an unreachable `origin` (no SSH key for the service account) lands in `App.originError` and that box alone, never failing the check. `POST /api/repository/update` brings upstream commits in in one step — fast-forward when the checkout has no commits of its own, otherwise a merge commit (a fork with local work is permanently diverged) — refused while the tree is dirty, and holding `App.mu` so no submission snapshots a half-merged tree. It no longer merges in the checkout itself: it delegates to `graft.go`, so a conflict changes nothing here and leaves a resolution open instead of a dead-end message. Note that `Ahead`/`Behind` are measured against **upstream** while `ForkAhead`/`ForkBehind`/`ForkTracked` are measured against `origin/<branch>`: a checkout fully pushed to its fork is still every one of those commits ahead of upstream, so only the Fork counts may drive the Push button.
  Each non-upstream box also carries `Source.Ahead`, the commits its selected branch has that upstream does not — what a pull request opened from that box would contain, computed for the selected branch only (one revision walk per box, not one per branch listed), and a third number not to be confused with either `Ahead` or `ForkAhead`. `GET /api/repository/commits?ref=` re-lists one box when another branch is picked (returning that count with it), and `POST /api/repository/checkout` moves the working tree. Three guards are load-bearing: only a revision `offered()` actually listed is accepted (the browser's list is never authoritative, as with `allowedFlatpak`); the revision must carry `sourceDir`/`Makefile` (`git cat-file -e <rev>:2.12/Makefile`), since `main.go:84`, `runner.go:185` and `runner.go:619` all hardcode `2.12/` — which is why `origin/3.0` and `origin/2.10` are listed but refused with a 409; and every branch switch goes through `git switch` (never `checkout`) because the release branches are named after that same directory and `git checkout 2.12` is ambiguous. A remote branch becomes or reuses a local branch of the same name so the command-line `2.12/Makefile-docker:2` `GIT_BRANCH` stays valid; a bare commit detaches HEAD, which the UI warns about — web builds are unaffected (they force `GIT_BRANCH=2.12`), `make` at the repo root is not.
- `changes.go` — the **working tree** box on the same screen: what differs from HEAD, staged a file at a time, and committed. `changes()` parses `git status --porcelain -z -uall` into one `Change` per path carrying git's own two status letters (a file can be staged *and* edited again afterwards, which is two different diffs), capped at `maxChanges` (500) with the rest counted in `MoreChanges` — a checkout with a build tree left inside it is not something anyone stages from a browser. It rides along with every repository response, because `state()` already ran `git status` for `Dirty`. `GET /api/repository/diff` serves one file's changes as plain text for the same viewer the build log uses (`side` picks `staged`, `worktree`, or everything since HEAD — an untracked file is diffed against `/dev/null`), `POST /api/repository/stage` adds or restores paths, and `POST /api/repository/commit` records the index alone (never `commit -a`). Three guards: a path is only acted on if the *current* `git status` just reported it (`changed()`, the same rule `offered()` applies to revisions); a rename moves with both of its paths, so unstaging one cannot leave the other half staged; and a commit is refused while a graft is open, since moving HEAD would strand the resolution `applyMerge` prepared against it. Every handler holds `App.mu` for the whole operation so a submission cannot snapshot a half-staged tree. Note that `repositoryPush` deliberately does *not* check for a dirty tree: a push publishes commits, and committing part of the tree here and pushing it is the ordinary way to work.
- `graft.go` — the one mechanism behind every merge and every cherry-pick, and the conflict resolution screen. A **graft** is one replay in progress, held open across requests in `App.graft` under `App.graftMu` (its own lock, so resolving a conflict can never block the build worker; lock order `mu` → `graftMu`). Nothing happens in the checkout: `worktree()` prepares a linked worktree at `<data>/graft` detached on the commit the checkout sits on, `openGraft()` runs `git merge` or `git cherry-pick` there, and only `applyMerge()` moves the checkout — by `git merge --ff-only` onto the commit the worktree produced, which is always a fast-forward because that commit's first parent is `Graft.Base`. That is what makes abandonment and a mid-merge restart free: `reapGrafts()` at startup deletes the worktree, sessions are ephemeral and never adopted (same rule as `reapVMs`). Two details are load-bearing: `Graft.OursLabel`/`TheirsLabel` are computed server-side because the sides **swap** between the two kinds (a merge replays upstream onto the checkout, a cherry-pick replays your commit onto upstream, so git's stage 2 means the opposite thing); and `applyGraft` refuses when `HEAD != Graft.Base` or the tree is dirty, since the preview it was built on no longer describes the checkout. `resolveFile` settles one file — `ours`/`theirs` from git's stages (or `git rm`, when that side deleted it), `both` via `git merge-file --union`, `edited` from text the browser sent — and `GET /api/repository/graft/file` serves any version (`merged`, `ours`, `theirs`, `diff`) as plain text for the same viewer the build log uses. A path is only ever accepted if the open graft listed it, exactly as `offered()` gates revisions.
- `pr.go` — pull requests towards the fixed upstream, reachable two ways in the UI — from a box header (the whole selected branch) and from any one commit — and in two shapes: `through` (this commit and its whole history — the branch *is* the commit, nothing is replayed, nothing can conflict) and `single` (this commit alone, cherry-picked onto the upstream branch, which opens a graft when it conflicts and opens the PR from `finishPick` once resolved). Authentication is the host's `gh`: `gh auth token` reads its configuration with **no network call**, which is why `github()` can run inside `state()` on every repository read. The token reaches git and gh through the process environment, never through `argv` or a URL, so it cannot surface in a process listing or in the git error text the UI shows. `pushTo`'s `force` is only ever set for a branch under `ydfs-web/` (a namespace this manager owns and re-pushes after a re-resolution); `POST /api/repository/push`, which publishes the checkout's own branch on the fork, is always fast-forward-only. Only tests substitute `forkFrom` (a local repository), the same seam as `upstreamFrom`.
  `pr.go` also answers `GET /api/repository/pulls`: the open pull requests on upstream whose head branch lives on this fork (`Others` counts the rest, so an empty list never reads as "nothing is open upstream"). It is the one repository read that costs a network call, which is why it is **not** part of `state()` — it has an endpoint of its own, a 30s cache (`pullsFresh`), and a `?refresh=1` that bypasses it; a failed refresh keeps the listing already on the screen and reports the failure against it.
- `ui/src/main.tsx` — the entire React frontend is one file (single `App` component: build form, saved profiles, job list/"Build activity", live log viewer via `EventSource`).
  **One screen at a time, chosen from the left-hand menu**: `menu` lists the eight entries (Repository, New build, Launch, Flatpak, Logs, Kept builds, Saved profiles, Build activity) in order, `page` says which is shown in the content area, and the location hash carries it (`#/logs`), so a reload, the back button and a pasted link all land in the same place — `go(id)` writes the hash and the `hashchange` listener keeps state and URL together. The boxes are built as `const`s before the `return` because some appear on more than one screen (the job list and build details belong to both "New build" and "Build activity"). The VM console lives only on **Launch**, so `startVm` navigates there — leaving the screen stops watching, never the machine. Job state drives UI directly: `done(state)` (`succeeded|failed|cancelled`) gates whether a job shows "Cancel build" vs "Delete build", and the job icon/badge. The UI polls `/api/jobs` every 5s as a fallback in addition to the per-selected-job SSE stream, and refetches on `visibilitychange` so a long-backgrounded/idle tab resyncs immediately instead of waiting on a possibly-stalled SSE connection.
  **One reader for every build file**: `TextViewer` is a single `<dialog>` used for both the build log and the archived `config.ini` — driven by a `TextView` (`{key, title, subtitle, url, compact?, onDelete?}`), it fetches the text, offers search with highlighted, steppable matches, and a download. `config.ini` opens with `compact: true`. It is also the one *writer*: a conflicting file opens with `editable: true`, which swaps the `<pre>` for a `<textarea>` and adds Save — an editor here rather than a third dialog pattern. Note the sizing trap: a modal `<dialog>` is fixed with `inset: 0`, so `height: auto` is over-constrained and stretches to the whole viewport — `compact` uses `height: fit-content`, and because `.logviewer-body`'s `height: 100%` cannot resolve against that, the cap and the scrolling sit on `.logviewer-text` instead. A Playwright assertion guards both.
  The **Test machine** box renders `VmConsole`, which lazily `import()`s `@novnc/novnc` (its `exports` is the single string `./core/rfb.js`, so subpath imports do not resolve) and keys its RFB connection on the server-issued `session` id, not the job id, so the 5 s job poll cannot tear down a live console.
  The **Repository** screen re-reads the checkout every `repoPollMs` (5s) while it is the page shown and the tab is visible, skipping the tick whenever an action of its own is in flight (`repoBusyRef`): the checkout is worked on at the command line as often as through the UI, and a commit made in a terminal must not leave the working-tree list still claiming those files are uncommitted. The open pull requests are fetched once on entering the screen instead, because they reach GitHub. A staging checkbox is controlled by the server's answer, not by the click: it ticks when the response arrives, so what is shown is always what git actually did.
  **No native browser dialogs**: the UI never calls `window.confirm`/`alert`/`prompt`. Every confirmation goes through the single `ConfirmDialog` component (a native `<dialog>`, so focus trap, Escape and backdrop come for free), driven by one `ask` state holding `{title, body, confirm, danger, onConfirm}`. Escape is intercepted with `preventDefault` and closed through state, otherwise the effect would immediately reopen it. Destructive confirmations focus Cancel. Reuse this rather than adding a second dialog pattern; a question with two answers (a pull request carrying one commit, or that commit and its history) uses `Confirmation.alternate` rather than a dialog of its own.
- `internal/assets/` — Go embed of the built `ui/dist` output; `assets.go` exposes it as an `fs.FS` for `main.go`'s static file server.
- `deploy/` — production templates: systemd units (`ydfs-web.service`, `oauth2-proxy.service`), Caddy and Nginx reverse-proxy configs, `*.env.example` files. Real deployment path: `Browser → Caddy/Nginx HTTPS :8088 → OAuth2 Proxy (GitHub) → Go on 127.0.0.1:8080`. `webui/README.md` has the full deployment walkthrough (OAuth app setup, secrets, systemd/proxy install order).

Each build submission snapshots the current `2.12/` working tree (including uncommitted local edits, excluding `config.ini`) into a private per-job directory before queueing, records the Git revision/tag and a `working-tree.patch`, and builds that snapshot inside `/tmp/ydfs` in the container — later edits to the checkout do not affect already-queued/running jobs.

## Flatpak pre-installation

The distro already builds a full Flatpak stack from source into the core squashfs (`2.12/packages/list-x86:981-990`; `list-updates` rebuilds flatpak/libostree, and `make_modules` runs `make updates` even in `BUILDYDFS=fast`, so `$HOME/x86_64/bin/flatpak` exists on both ISO paths). What was missing was seeding, which the `flatpaks` setting supplies:

- `2.12/data/flathub-apps` — one Flathub app ID per line (`#` comments allowed). Hand-editable for CLI builds; the web UI rewrites it inside its own per-job snapshot only.
- `2.12/scripts/make_flatpak` — re-validates every ID (the file is hand-editable), then `flatpak --user install` into `$HOME/flatpak` with `FLATPAK_USER_DIR` set, avoiding polkit and `flatpak-system-helper`. Also uninstalls apps dropped from the list, since `$HOME` is a cache shared by every build.
- `2.12/Makefile` — a `flatpak` target runs that plus `SKIP_STRIP=OK make_module flatpak` (stripping would corrupt the OSTree hardlink web). `FLATPAKMODULE` is empty unless the list has entries, so `${ISOPATH}` gains the dependency only then.
- `2.12/scripts/make_config_ini` — appends `flatpak-${ARCH}` to the `MODULES=` line only when the list is non-empty; `make_iso` hard-fails on a module named in `MODULES` but never built.
- `2.12/init-x86/ydfs/enable/flatpak-preinstalled` — sourced from `rcS` just before `flatpak-disk`. `mountopt` has already mounted and overlaid the module by then, so this only points Flatpak at it: a symlink from `var/lib/flatpak` normally, or an extra read-only installation in `/etc/flatpak/installations.d/` when `/disk/flatpak.loop` owns that path. Being sourced, it must never call `exit`.

Deliberately a *separate* module, not the core rootfs: `fast-iso` downloads the core squashfs prebuilt and cannot modify it, and `detect/modules:26` copies the core's `/var` into the 75%-of-RAM tmpfs root on every boot.

## CI

`.github/workflows/webui.yml` runs on changes under `webui/**`: `make build`, `go vet`, `go test -race`, the real Docker lifecycle test, and Playwright tests. `.github/workflows/fast-iso.yml` is currently a stub (its actual `make fast-iso` build step is commented out). `.github/workflows-disabled/` holds other workflows not currently active.
